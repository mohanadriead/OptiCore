# Attendance and manager corrections

Normal endpoints require the existing Employee policy and an active authenticated employee. Self-service resolves the subject from the authenticated server-side employee ID:

- `GET /api/attendance/me/status`
- `POST /api/attendance/me/check-in`
- `POST /api/attendance/me/check-out`

Numbered endpoints allow regular employees to access only their own number; active managers may access other employees:

- `POST /api/attendance/{employeeNumber:int}/check-in`
- `POST /api/attendance/{employeeNumber:int}/check-out`
- `GET /api/attendance/{employeeNumber:int}/status`

No mutation body is required. Managers select a subject by EmployeeNumber independently of the authenticated audit actor. Regular employees cannot select another subject. Cross-employee requests from regular employees return HTTP 403 before target lookup, including nonexistent employee numbers. Self-service ignores client-supplied employee numbers and identities. Clients cannot supply audit identity. Only active subjects can check in. Managers can check out existing sessions after subject deactivation. Duplicate entry and missing open-session exit return HTTP 409 with safe Hebrew ProblemDetails titles. Attendance does not gate login, authorization, or access to other modules.

Regular employees automatically load their own name, employee number and status through `/me/status`, with no employee search controls, and act through `/me/check-in` and `/me/check-out`. Managers retain employee-number lookup. Role or identity changes reset the workflow and discard previously displayed subjects. Self-status loading failures and conflicts support explicit refresh. Both views use Hebrew RTL and keep explicit context-appropriate attendance buttons.

Status contains only EmployeeNumber, FirstName, LastName, HasOpenAttendance, and CheckInAtUtc (nullable). An overdue session is effectively closed at Israel midnight even if its closure has not yet been persisted by recovery. Status is read-only. The manager Hebrew RTL attendance screen requires lookup before displaying the subject's name, current status, and explicit Check-in/Check-out buttons; only the applicable action is enabled. Changing the employee number invalidates the lookup. Successful actions retain the employee details and update the current status from the returned attendance times, allowing Check-in followed by Check-out without another lookup. A conflict requires a fresh lookup. Lookup and action responses are validated for shape, time consistency, and the requested employee number; a malformed HTTP 200 response shows a safe Hebrew error and does not offer an action. Enter performs lookup only, never an attendance mutation. This restores explicit action selection from `8039011`, whose original attendance page had no separate status lookup, while retaining the follow-up's safe lookup and Employee authorization.

Manager-only endpoints use both the Manager policy and service-level active-manager validation:

- `GET /api/attendance/management/records?employeeNumber=42&from=2026-07-01&to=2026-07-02&page=1&pageSize=25`
- `GET /api/attendance/management/records/{id:guid}`
- `POST /api/attendance/management/records/{id:guid}/corrections`

History filters by the check-in's Israel-local calendar date. Start/end dates are inclusive; selecting the same date twice filters one day. Either bound can be omitted. Pages are ordered by descending check-in and ID, with a maximum size of 100 (default 50). Details include persistent correction history and the correcting manager's employee number and name. The manager screen provides filters, pagination, details, missing-checkout entry, and correction audit without displaying GUIDs. Each row has an explicit Edit action. The prepopulated form uses separate Israel-local date and 24-hour HH:mm fields, requires a reason, supports cancellation and confirmation before saving, and refreshes history and details after success. Unchanged minute fields preserve the original UTC seconds, fractional precision and repeated-hour occurrence. Employee users cannot enter this route or access its endpoints. Anonymous requests return 401. No attendance or correction DELETE endpoints exist.

Corrections require CheckInAtUtc, nullable CheckOutAtUtc, Reason (trimmed, nonempty, at most 2000 characters), and the inspected values ExpectedCheckInAtUtc, ExpectedCheckOutAtUtc, ExpectedUpdatedAtUtc. Stale values return 409 so a manager must reload before retrying. The subject cannot change. Times must be UTC, must not be in the future, and checkout must be between check-in and the recalculated Israel-midnight boundary, inclusive. A closed record cannot be reopened; an open record cannot be left open past its corrected boundary. These rules are enforced by the backend regardless of the form's validation.

Every correction saves an AttendanceCorrection containing previous/new check-in and checkout, manager identity, correction time, and reason in the same database transaction as the attendance update. Correcting an automatic record while retaining its recalculated midnight checkout keeps WasCheckoutAutomatic and the original actual processing time. Overriding its checkout makes it manual with actual correction processing time. AutomaticCheckoutDueAtUtc always follows the corrected check-in date; UpdatedByEmployeeId identifies the correcting manager even when the retained checkout remains automatic. UTC storage and boundary/processing meanings remain distinct. The frontend edits in Asia/Jerusalem independently of the browser timezone; unchanged values preserve exact UTC timestamps. A new time during a repeated winter-transition hour chooses its first occurrence, explained in the form. Nonexistent spring-transition times are rejected.

All persisted timestamps are UTC. Asia/Jerusalem supplies local calendar boundaries with DST rules. Each session has a persisted cutoff at the first local midnight after entry. Normal checkouts at or after that boundary close automatically, with effective checkout equal to that cutoff, a null update actor, and CheckoutProcessedAtUtc/UpdatedAtUtc equal to actual processing time. Overnight work requires a new entry. A recovery worker runs immediately on host startup and every 30 seconds; physical processing can lag midnight by that interval while effective checkout remains midnight. Failed recovery is retried with a value-free warning. Check-in/out requests also recover their subject's overdue session transactionally. A checkout which recovers an old session commits the closure before returning the no-open-session conflict. Manager corrections subsequently record their own audit actor as described above.

Transactions lock Employees in SHARE mode before AttendanceRecords in SHARE ROW EXCLUSIVE mode. This keeps actor/subject state stable against existing employee writers and serializes attendance mutations, corrections, and recovery across processes. The filtered unique index on EmployeeId where CheckOutAtUtc is null independently enforces one open session; its named unique violation still becomes the safe duplicate-attendance conflict. Locking was reviewed and retained: employee management acquires table-wide locks before reading and updating employees, and substituting attendance row locks would need a shared lock-order protocol, empty-session protection, and real cross-process verification. That coordination would involve unrelated employee writers and is not proven by the offline suite. These conservative locks serialize different employees' mutations too. History/status reads do not take the exclusive attendance transaction lock.

Read-only preflight on 2026-10-10 verified the configured local development database `opticore` (localhost, port 5432) and confirmed `20261010082618_AddAttendance` in __EFMigrationsHistory. The transaction was rolled back without any write. Both existing AddAttendance files are preserved. The separate AddAttendanceCorrections migration was generated offline using the existing design-time factory, which never starts the API or connects to PostgreSQL. Its five Up operations only replace the AttendanceRecords checkout CHECK constraint and add AttendanceCorrections with restrictive foreign keys, CHECK constraints, and indexes. It does not change Employees or other business tables, or the open-session partial unique index. The implementation agent did not apply migrations. On 2026-10-11, the repository owner reported that 20261010200538_AddAttendanceCorrections had been applied to the local database and corrections had been exercised successfully; this delivery did not independently query the database. Other environments require the additive migration through the normal deployment process before using manager corrections. Its Down is a schema rollback that removes correction history and restores the old stricter CHECK; rollback after corrections requires deliberate review and may reject rows valid under the new constraint.

Run the backend suite with `dotnet test tests/OptiCore.Tests/OptiCore.Tests.csproj -c Release` from backend. The Attendance PostgreSQL test follows the existing OPTICORE_VERIFY_DATABASE opt-in convention and additionally verifies real SQL history projections, correction persistence, and rollback of record and audit together. It creates and removes only its generated temporary schema in opticore_dev, refuses a different configured database, and does not apply migrations or modify public data. It must not be enabled against the configured local opticore for this task. Default tests do not connect to PostgreSQL. All three opt-in PostgreSQL tests remain disabled unless separately approved. Frontend verification uses `npm.cmd run build`, `npm.cmd run lint`, and `npm.cmd run test:run` on Windows.
